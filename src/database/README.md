# Message repository

## Current boss session extension

All boss lead fields are individually optional. A meaningful factual draft can await confirmation or be saved by explicit confirmation from `collecting` or `awaiting_confirmation`. The service refreshes validation under the current policy, including for older stored drafts. Completion checks the stored snapshot's schema and nonempty facts, saves only that snapshot with nulls preserved, closes the session and inserts its reply atomically. An empty draft cannot be saved. No migration is required for this policy change; see the [optional-fields report](../../docs/optional-boss-lead-fields.md).

Boss processing first calls `beginLeadExtractionProcessing(messageId, claimedToken, leaseMs)` to atomically consume a valid claim and obtain an invocation-specific token. Use the returned token for heartbeats, checkpoints and completion; keep the caller's original claim unchanged. Duplicate invocations cannot both run extraction. This changes no schema, preserves normal expired-lease recovery, and does not affect customer/Phase 1 extraction.

Migration 007 adds `reply_history` for the complete text and delivery record of replies replaced by explicit operator retries. Archive insertion, audit, outbox removal and requeue are atomic. Unsent archived replies become `CANCELLED` and are never dispatched. Chat queries combine this archive with the existing inbox/outbox and return each message's `sender_type` from its original processing role.

Migration 006 extends this with `address`/`trn_no`, per-message `transcription`/`extracted_text`, lease-fenced `checkpointLeadMedia`, and retained `discarded` sessions with a `pending_action` for switching customers. `completeLeadSessionTurn` can archive an unsaved draft and create a fresh empty draft atomically. The runner now applies versions 1–7. Historical JSON results missing new nullable fields decode compatibly. See the [current implementation report](../../docs/lead-intake-next-phase.md).

Migration 005 adds persistent `lead_sessions`, durable `message_receipts` sequence and contact/media/session metadata to the existing inbox. Boss intake no longer inserts placeholder leads. `getActiveLeadSession` and `completeLeadSessionTurn` handle draft updates, atomic confirmation, lead insertion and closure; `failLeadWorkflow` still handles durable retries. `listConversations`, `getConversation` and `listConversationMessages` read history from the existing inbox/outbox. Versions 1–5 apply through the same migration runner. See [current boss chat contract](../../docs/boss-chat.md); descriptions of immediate boss saving below are historical.

## Existing repository contracts

`createMessageStore({ databaseUrl, logger })` returns an asynchronous repository. Call `await store.init()` before use and `await store.close()` during shutdown. `ping()` checks database connectivity. Supported URLs are `postgres://` / `postgresql://` for production and persistent `file:./data/messages.sqlite` for local development. In-memory databases are intentionally rejected.

All message dates are returned as ISO strings; `extracted_lead_data` is an object or null; `authenticated` and `crm_write_started` are booleans. Database clocks determine lease expiry and outbox eligibility.

Conversational replies use migration 002's nullable `processing_flow` column. `enqueueMany` accepts `processingFlow: 'conversation'` to tag only newly inserted authenticated, nonblank text; it cannot be combined with `replyText`. Duplicate receipts and old rows retain their original scope. `claimNext` and `claimReply` accept the same option to restrict selection and cleanup to that flow; omitted/null preserves the earlier contract below. Reply claims include `processing_flow` for dispatch authorization. Conversation jobs outside the 23-hour window are marked terminal before a provider call; expired final attempts are marked exhausted. No CRM ID exception bypasses the conversation attempt cap.

Migration 003 adds `lead_extractions` for independent internal boss extraction. The retained Phase 1 contract accepts trusted `request_lead_extraction: true` on a newly inserted, authenticated, nonblank conversation message to create its unique extraction job. New webhook receipts now use Phase 2's `request_lead_workflow` contract described below. Duplicate or old receipts are never backfilled. Phase 1 jobs reference the unchanged original inbox message; their result and processing state never alter the conversational inbox status, outbox or legacy CRM fields.

`getLeadExtraction(messageId)` reads the internal row and decoded `result`. `claimLeadExtraction({ leaseMs, maxAttempts })` leases one due job and joins its source message. `heartbeatLeadExtraction(id, token, leaseMs)` renews ownership. `finishLeadExtraction(id, token, patch)` uses the current unexpired lease to persist `SUCCESS`, `IRRELEVANT` or `FAILED`, with a bounded JSON result and safe error code. Only `FAILED` can schedule a retry. Expired final attempts become terminal; these internal jobs have no WhatsApp delivery-window cutoff because they never send messages.

Migration 004 adds exclusive `boss_lead` intake and durable `leads` records. Generic inbox claims exclude this flow; extraction claims support both Phase 1 and Phase 2 jobs. Phase 2 uses `completeLeadWorkflow` / `failLeadWorkflow` to fence the extraction lease and atomically persist lead, inbox and confirmation state. The older `finishLeadExtraction` method cannot complete `boss_lead` work. See the [Phase 2 database contract](../../docs/lead-database.md) for migration details and dashboard read APIs.

| Method | Contract |
| --- | --- |
| `enqueueMany(messages, { includeInsertedIds = false, replyText = null } = {})` | Atomically inserts a batch, ignores existing `whatsapp_message_id` values, and returns `{ inserted, duplicates }` counts. With `includeInsertedIds: true`, also returns `insertedIds` for receipt logs only after new inserts commit. `authenticated` is true only when the caller passes literal `true`. Optional `replyText` queues a fixed reply only for newly inserted, authenticated, nonblank text messages and completes those inbox rows as `SUCCESS` in the same transaction. Acknowledge the webhook only after this operation commits. |
| `getMessage(id)` | Returns the message row or null. |
| `claimNext({ leaseMs = 120000, maxAttempts = 3 })` | Claims one received message, due retry, or expired processing lease. Returns a row with a new UUID `lease_token` and incremented `attempts`, or null. Failed rows without `next_attempt_at` are terminal. Rows with a persisted CRM ID may be claimed beyond the attempt cap solely for local finalization. |
| `mark(id, token, patch)` | Applies approved fields only. Returns false if the processing lease expired or its token changed. Leaving `PROCESSING` clears the lease. |
| `heartbeat(id, token, leaseMs)` | Renews an unexpired processing lease and returns whether ownership remains valid. |
| `withContactLock(key, callback)` | Serializes a contact across database connections. The callback receives `{ assertOwned }`; call it before external writes. Acquire multiple contact keys in sorted order. |
| `getContactState(key)` | Returns `{ zoho_lead_id, uncertain }` or null. |
| `beginContactWrite(key)` | Persists contact uncertainty before an external CRM mutation. Retains any known CRM ID. |
| `saveCrmResult(id, token, { zohoId, action, contactKey, contactKeys })` | Atomically saves the CRM result on the message and all unique contact keys, clearing uncertainty. Returns false for stale ownership and makes no contact changes in that case. |
| `completeWithReply(id, token, patch, text)` | Atomically changes the message to a terminal status and inserts its unique reply. Returns false for stale ownership. |
| `queueReply(id, text)` | Idempotent insert for an already terminal message. Prefer atomic `completeWithReply` during processing. |
| `claimReply({ leaseMs = 120000, replyText = null } = {})` | Claims a pending reply younger than 23 hours from its inbound message. Optional `replyText` restricts candidate selection to that exact reply text. Returns a reply row including `id`, `message_id`, `sender_phone`, `authenticated`, `message_type`, `text`, and `lease_token`, so the dispatcher can check sender eligibility before sending. Expired sending leases become `UNKNOWN`; expired pending replies become `FAILED`. |
| `finishReply(id, token, result)` | Finishes an owned sending lease with `SENT`, `FAILED`, or `UNKNOWN`. Accepts optional `error_message` and `provider_message_id`. Returns false for stale ownership. |
| `recordReplyReconciliation(id, token, providerMessageId)` | Preserves an accepted provider ID on the same original sending attempt as `UNKNOWN`, even after lease expiry. Returns `UNKNOWN`, or `SENT` if that exact receipt was already committed, or null when ownership/state/evidence conflict. Never requeues a reply. |
| `getReply(messageId)` | Returns the outbox row or null. |
| `appendLog(id, event, details)` | Persists only approved operational metadata; arbitrary detail fields are dropped. |
| `getContactLead(key)` / `saveContactLead(key, id)` | Read/save a contact mapping. The latter is intended for a confirmed reconciliation under the same contact lock. |

Allowed message patch fields: `extracted_lead_data`, `zoho_lead_id`, `crm_action`, `processing_status`, `error_message`, `processed_at`, `next_attempt_at`, and `crm_write_started`. Terminal completion requires `SUCCESS`, `NEEDS_INFORMATION`, or `FAILED` without a scheduled retry.

Fixed reply options accept null (disabled) or nonblank text of at most 4096 characters, without NUL. Omitting them preserves the existing intake and claim behavior. A duplicate receipt never gains a reply, including a receipt first stored while fixed replies were disabled. Fixed-reply intake commits the receipt, inbox completion, and unique outbox row together; any reply insertion failure rolls back the entire batch so webhook redelivery remains safe. Here `SUCCESS` means intake handling is complete, not that WhatsApp accepted or delivered the reply; the outbox tracks sending separately. Completed fixed-reply receipts cannot enter the later lead-processing queue. A dispatcher scoped by exact reply text leaves other pending replies unclaimed; normal expiry cleanup still applies to all replies.

PostgreSQL uses transactions and `FOR UPDATE SKIP LOCKED` for claims. Contact serialization uses dedicated session advisory locks, so use a direct connection or a pooler in **session mode**. The connection pool has 12 connections; each nested contact lock occupies one connection in addition to repository queries. Application workers should keep concurrency bounded.

SQLite uses WAL, full synchronization, foreign keys, and renewable contact-lock rows. Its transaction generator runs synchronously from BEGIN through COMMIT, avoiding asynchronous interleaving on a single connection. Use PostgreSQL for production and multiple deployment replicas.

CRM calls and WhatsApp sends cannot be part of a database transaction. Persist uncertainty before CRM writes and reconcile ambiguous outcomes before allowing more writes for the contact. A reply whose result is ambiguous is never resent automatically. These rules favor avoiding duplicate external actions over automatic recovery in uncertain cases.

Expired send leases retain their original token solely as attempt identity on `UNKNOWN` rows; it is not renewed send authority. Reconciliation only accepts the same token in `SENDING`/`UNKNOWN` with a null or matching provider ID. Old rows whose attempt token was already discarded require manual reconciliation. No schema migration is needed. The existing `FAILED` status distinguishes definite `NOT_ATTEMPTED` and `ATTEMPTED_FAILED` outcomes through its safe error code. Provider acceptance with unconfirmed completion is retained as `UNKNOWN` plus the provider ID and `PROVIDER_ACCEPTED_RECONCILIATION_REQUIRED`; it must not be blindly resent.

Schema changes belong in migrations. Versions 1 through 4 are applied transactionally on initialization; PostgreSQL serializes migration execution across processes. Existing data remains intact and is not opted into new extraction work after upgrade. The application database should be dedicated to this service. Retention, encrypted backups, and access restrictions must account for the customer information stored in messages, extracted results, and contact mappings.

`node --test test/database.test.js` exercises the local contract. Setting `TEST_DATABASE_URL` additionally runs the same contract on PostgreSQL, creating and dropping uniquely named test schemas. Use a dedicated development database whose test role may create schemas.
